# Plan 03 - Guardrails and Verification

## Goal

Lock Phase 3 provenance, public-data posture, and legal-finality safety with focused automated tests, static guardrails, and verification evidence.

## Must Haves

- Tests prove sanctions/trade exposure claims include source/list/date/version provenance or explicit public-source fallback.
- Tests prove the UI and model frame results as public screening signals, not final legal determinations.
- Tests prove SCM variant still contains sanctions and trade-control surfaces by default.
- Guardrails scan new compliance exposure files and touched panels for private-data-shaped or legal-finality phrases.
- Typecheck, boundary lint, focused tests, and SCM build smoke pass or unrelated blockers are documented.

## Risks

- Guardrails can overblock legitimate compliance vocabulary. Prefer context-specific checks and allow neutral words like "screening", "exposure", "designation", and "requires review".
- Existing Windows script issues may block generic build or E2E commands. Use the documented direct SCM build path and record blockers.
- Browser visual review may remain manual unless Phase 3 execution explicitly starts a dev server and inspects the SCM variant.
